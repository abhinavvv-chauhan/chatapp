## PART 0: THE FULL STORY (How the entire project works, explained simply)

If you have never built this project and don't know what it does, read this story. 

Imagine you own a bustling virtual office. Every time a team member types a message, creates a workspace, or joins a channel, a tiny signal (an "event") needs to instantly appear on everyone else's screen. This project is a **Real-Time Collaboration Engine** that handles thousands of these rapid-fire events and uses AI to summarize what you missed while you were sleeping.

Here is the exact journey of one piece of data (like John typing "Hello Team"):

1. **The Front Door (HTTP & JWT):** When John logs in through the web dashboard, the backend verifies his identity and gives him a VIP pass (JWT token). He then uses this pass to open a permanent, two-way tunnel (WebSocket) to the server.
2. **The Traffic Cop (WebSocket Hub):** When John sends "Hello Team" through the tunnel, our Go backend doesn't just save it. The message goes straight to the **Hub**. The Hub looks at its directory and says, "Who else is currently connected and looking at the #general channel?" 
3. **The Instant Broadcast (Channels):** The Hub instantly blasts John's message down the individual tunnels of everyone else in that channel. They see the message appear on their screen instantly, without ever refreshing the page.
4. **The Permanent Record (PostgreSQL + SQLC):** At the same exact time, the backend safely stores John's message into our PostgreSQL database using highly-optimized SQL queries generated by SQLC, so it's permanently saved for anyone who is offline.
5. **The Background Worker (Push Notifications):** If Sarah is offline, a background worker (a separate Go routine running on a loop) wakes up, grabs Sarah's subscription details, and fires off a WebPush notification to her phone saying "John sent a message."
6. **The AI Copilot (Catch-up):** When Sarah finally wakes up 8 hours later, she clicks the "Catch-up" button. Our Go server grabs the last 50 messages from the database and sends them to the Groq API (using the blazing-fast Llama 3 model) with strict instructions. The AI instantly reads the transcript and returns a structured JSON summary of action items and decisions, so Sarah doesn't have to read 50 messages manually.

That is the entire project. It authenticates users, manages real-time broadcast tunnels, saves data reliably, sends notifications in the background, and summarizes chaos using AI.

## PART 3: THE COMPLETE PROJECT STRUCTURE — What every file does

When they ask "walk me through the structure of your codebase" — say this:

---

### `cmd/` — The Entry Points
This folder holds the main executables of the application.
- `cmd/server/main.go`: The front door. This is the main backend server. When executed, it connects to PostgreSQL, boots up the background worker pool, initializes the WebSocket Hub, mounts all REST/HTTP API routes, and listens for traffic.
- `cmd/migrate/main.go`: A standalone script to run database migrations programmatically.
- `cmd/testmodels/main.go`: A sandbox script for testing database interactions locally without booting up the entire web server.

### `db/` — Database Schema & SQL Queries
This is where the database is strictly defined without using an ORM.
- `db/migrations/*.sql`: Contains up/down SQL files that define the raw PostgreSQL schema (e.g., `001_create_users.up.sql`, `003_create_messages.up.sql`). This includes tables for users, workspaces, channels, messages, and push subscriptions.
- `db/queries/*.sql`: Contains raw SQL queries for various entities (e.g., `messages.sql`, `users.sql`). These files are fed into SQLC. SQLC parses these queries and automatically generates type-safe Go functions for them, ensuring optimal speed and preventing SQL injection.

### `internal/` — Private Application Code
This is the core logic. Code here is "internal" and cannot be imported by other Go projects.
- `internal/config/config.go`: Loads environment variables (like Database URLs, JWT secrets, and VAPID keys) and sets up the configuration struct used throughout the app.
- `internal/handler/`: Contains the HTTP controllers.
  - `ai_catchup.go`: Handles the LLaMA 3 integration. It fetches a channel's chat history, formats it, prompts the Groq API for a strict JSON summary, and caches the result in-memory.
  - `auth.go`: Handles user registration, login, and issues JWT tokens.
  - `message.go`: Handles fetching message history (pagination) and legacy HTTP message posting.
  - `upload.go`: Handles multipart file uploads (e.g., images) to the server.
  - `workspace.go`: Handles the creation of Workspaces and Channels, as well as Role-Based Access Control (RBAC) logic for joining and approving community requests.
  - `poll.go`: Handles the creation and voting mechanism for chat polls.
- `internal/repository/query/`: Contains the auto-generated code from SQLC (e.g., `models.go`, `messages.sql.go`). It also contains `custom_*.go` files where you hand-wrote complex or dynamic queries that SQLC couldn't easily generate.
- `internal/server/`: Sets up the HTTP server and routing.
  - `routes.go`: Maps HTTP verbs (GET, POST) to specific handlers and applies middleware.
  - `middleware/auth.go`: A JWT Auth Guard that intercepts requests, validates the token in the Authorization header or URL query, and attaches the user's ID to the request context.
- `internal/worker/pool.go`: The background task engine. It spins up a fixed pool of goroutines (workers) that read from a Go channel to process slow, asynchronous tasks—specifically, dispatching VAPID Web Push notifications—so the main HTTP response isn't blocked.
- `internal/ws/`: The real-time signaling engine.
  - `hub.go`: The central clearinghouse for all WebSockets. It maintains a list of connected clients and routes incoming messages to the correct channels. Crucially, it serializes map writes through channels to prevent concurrent map panics.
  - `client.go`: Represents a single user's WebSocket connection. It contains a `readPump` (listening for incoming chat or WebRTC signaling) and a `writePump` (pushing new messages to the browser).
  - `manager.go`: A higher-level wrapper that manages multiple Hub instances if needed, or groups connections logically.

### `pkg/` — Shared Public Libraries
These are utility functions that are agnostic to this specific application and could be reused in any Go project.
- `pkg/password/password.go`: Wraps bcrypt logic to hash passwords securely and verify them during login.
- `pkg/token/jwt.go`: Contains utilities to generate and cryptographically sign JWTs, as well as parse and validate incoming tokens.

### `web/` — The Frontend Client
- `web/index.html`: The monolithic Vanilla JS/HTML/CSS frontend. It establishes the WebSocket connection, renders the chat UI via DOM diffing/appending, manages the local audio context for Voice Channels, and renders the JSON from the AI Catch-up.
- `web/sw.js`: The Service Worker file. It runs in the background of the user's OS/browser to listen for and display native Web Push notifications even if the app tab is closed.


### `internal/ws/hub.go` — The Orchestrator
> "This is the brain of the real-time process. When running, this file orchestrates the registration and unregistration of users. It holds a map of all active clients and listens on channels to safely broadcast messages to thousands of connected users simultaneously."

**The actual code does:**
```go
		case msg := <-h.broadcast:
			for client := range h.clients {
				if client.channelID == msg.ChannelID {
					select {
					case client.send <- msg.Data:
					default:
						close(client.send)
						delete(h.clients, client)
					}
				}
			}
```
**Important detail to know:** The Hub uses Go's `select` statement. If a client's tunnel is blocked (e.g., their internet is lagging), the `default` case kicks in, aggressively dropping the bad connection rather than letting one slow user crash the entire server.

### `internal/ws/client.go` — The Safe Loader
> "This file is responsible for safely reading and writing data through the WebSocket connection. It uses Go's goroutines to separate the reading (listening to the user) and writing (sending to the user) processes, ensuring full-duplex communication."

**The actual code does:**
```go
// (Conceptual representation based on standard Go WebSocket patterns)
func (c *Client) readPump() {
    defer func() { c.hub.unregister <- c; c.conn.Close() }()
    for {
        _, message, err := c.conn.ReadMessage()
        if err != nil { break }
        c.hub.broadcast <- BroadcastMessage{ChannelID: c.channelID, Data: message}
    }
}
```
**Why this matters:** By separating reading and writing into two different goroutines per client, we prevent deadlocks. If a user is typing a massive paragraph, it doesn't stop the server from simultaneously sending them new messages from other people.

### `internal/worker/pool.go` — The Janitor
> "This file standardizes the messiness of background tasks. It spins up a fixed number of workers (goroutines) that sit there waiting for tasks. When a push notification needs to be sent, it gets dropped into a queue, and a free worker picks it up."

**The actual code does:**
```go
func (p *Pool) Start() {
	for i := 1; i <= p.WorkerCount; i++ {
		go p.worker(i)
	}
}

func (p *Pool) worker(id int) {
	for task := range p.TaskQueue {
		switch task.Type {
		case "web_push":
            // Send the notification to the WebPush provider...
		}
	}
}
```
**Why this matters:** If 100 people send messages at once, making 100 HTTP requests to a WebPush provider would freeze our chat server. By dumping these tasks into `p.TaskQueue`, the chat server responds in 1 millisecond, and the 3 workers handle the slow network calls in the background.

## PART 4: THE FULL FLOW AS A STORY

> "Let me walk you through exactly what happens when John sends a message to a channel with 1,000 users."

```text
1. John types "Deploy the code" and hits Enter.
2. The browser sends a JSON payload through the open WebSocket tunnel.
3. The Go `client.go` readPump goroutine intercepts the byte slice and passes it to the central `Hub`.
4. The `Hub` receives the payload on its `broadcast` channel.
5. The `Hub` loops through its in-memory map of 10,000 active connections. It identifies the 800 users currently viewing John's channel.
6. For those 800 users, the `Hub` instantly pushes the byte slice down their individual WebSocket tunnels.
7. Simoultaneously, an HTTP POST request (or internal handler) saves "Deploy the code" to the PostgreSQL `messages` table via a SQLC generated query.
8. The Hub spots that Sarah is missing from the active user map. It crafts a WebPush payload and drops it into the `TaskQueue` channel.
9. Worker #2 in `pool.go` wakes up, pulls the task from the queue, and makes a network call to Google/Apple push services. Sarah's phone buzzes.
10. Later, Sarah clicks "Catch up". The `ai_catchup.go` handler pulls the chat history, sends it to Groq's Llama 3 API, caches the resulting JSON in memory, and returns an actionable summary to her screen.
```

## PART 5: THE 5 CONCEPTS YOU MUST UNDERSTAND COLD (EXPLAINED LIKE YOU'RE 5)

If you don't know what you built, read this section carefully. This translates complex system engineering into plain English so you can actually understand the words you are saying in an interview.

### 1. WebSockets vs HTTP Polling (How real-time works)
**What you built:** A custom WebSocket architecture.
**How to understand it:** Imagine you are waiting for a very important package. 
- **HTTP Polling (The Bad Way):** You call the post office every 5 seconds and ask, "Is my package here?" They say "No." 5 seconds later, you call again. This exhausts the post office and wastes a massive amount of phone lines.
- **WebSockets (The Good Way):** You call the post office once, and you both agree to *never hang up the phone*. When the package arrives, the post office simply speaks into the phone: "It's here." 
**Why you chose WebSockets:** In a chat app with 10,000 users, if everyone's browser "called" the server every second (HTTP Polling), the server would crash instantly. WebSockets keep the connection open, using virtually zero CPU, allowing the server to push messages instantly only when they happen.

### 2. Go Channels and Goroutines (How the server handles traffic)
**What you built:** The server uses goroutines for concurrency and channels to communicate.
**How to understand it:** Imagine a restaurant kitchen. 
- **Node.js/Python (Single-threaded):** There is one extremely fast chef. He chops, cooks, and plates. But if he has to wait 10 minutes to bake a cake, the whole kitchen stops.
- **Go Goroutines:** You can instantly hire 10,000 invisible chefs (goroutines). One chef chops, one chef bakes, one chef plates. They talk to each other by sliding notes down a metal pipe (Channels). 
**Why you did this:** By dedicating two goroutines to every single user (one to listen, one to talk), the server handles massive concurrency. If one user's internet is slow, their specific chef just waits, while the other 9,999 chefs keep working flawlessly.

### 3. Background Worker Pools (How to handle slow tasks)
**What you built:** A fixed-size pool of workers listening to a task queue.
**How to understand it:** Imagine a busy coffee shop. The cashier takes your order and your money in 5 seconds. But making the latte takes 3 minutes.
- **The Bad Way:** The cashier stops, turns around, makes the latte for 3 minutes, and the line goes out the door.
- **The Good Way (Worker Pool):** The cashier takes your order, writes it on a cup, and drops the cup on the counter (The Task Queue). There are exactly 3 Baristas (The Workers) who do nothing but pull cups off the counter and make lattes. The cashier immediately helps the next customer.
**Why you did this:** Sending a WebPush notification over the internet takes a long time (maybe 500ms). If the chat server waited for the notification to send before confirming the message, the chat would lag horribly. The worker pool completely separates the fast chat from the slow notifications.

### 4. SQLC vs ORMs (How to talk to the database)
**What you built:** You wrote raw SQL and used SQLC to generate Go code.
**How to understand it:** Imagine ordering food in a foreign country.
- **ORM / GORM (The Bad Way):** You use Google Translate (the ORM). You say "I want a burger without cheese," and the translator tells the chef "Cow bread subtract yellow." The chef gets confused and it takes 20 minutes to cook.
- **SQLC (The Good Way):** You learn to speak the native language perfectly (Raw SQL). You write exact instructions. SQLC is just an assistant that double-checks your spelling before you hand it to the chef.
**Why you did this:** Chat databases require incredibly complex queries (joining users, messages, channels, sorting by timestamps, pagination). ORMs generate notoriously slow code for this. SQLC guarantees our queries are hyper-optimized while ensuring we don't make typing mistakes in Go.

### 5. In-Memory Caching (Making AI fast and cheap)
**What you built:** A mutex-locked cache for the AI summaries.
**How to understand it:** Imagine a teacher grading a massive math test. 
- **The Bad Way:** A student asks for the answer to Question 5. The teacher calculates it for 5 minutes and says "42." Another student asks the same question. The teacher calculates it all over again for 5 minutes.
- **The Good Way (Caching):** The teacher calculates it once, writes "Q5 = 42" on the whiteboard. When the next student asks, the teacher just points at the board.
**Why you did this:** Calling the Groq Llama 3 API costs money and takes 1-2 seconds. In `ai_catchup.go`, you built a `summaryCache`. If 5 people in the same channel click "Catch up" at the same time, you only ask the AI once. The other 4 people get the saved answer instantly, saving massive amounts of API credits and eliminating loading screens.

## CATEGORY 1: THE "WHY THIS?" CHALLENGE

**Q1. You used Go instead of Node.js or Python for a real-time chat app. Walk me through that decision.**

> **What the interviewer is asking:** "Why didn't you use Node.js and Socket.io like every other bootcamp grad?"
> 
> **Your Strong Answer:** "Node.js is great for I/O, but its single-threaded event loop can become a bottleneck under heavy concurrent CPU loads. Go’s concurrency model—specifically goroutines and channels—was practically built for real-time networking. A single goroutine consumes only about 2KB of memory, meaning I can maintain 100,000 active WebSocket connections on a cheap $5 server without breaking a sweat. Furthermore, Go’s strict static typing and compiled nature eliminated an entire class of runtime errors before the code even deployed."
> 
> **Translation of technical terms in this answer so you understand them:**
> - **Event loop:** How JavaScript handles multiple things at once by rapidly switching tasks.
> - **2KB of memory:** Extremely tiny memory footprint. Meaning the server can hold a lot of connections before running out of RAM.

---

**Q2. Why custom WebSockets in Go instead of a managed service like Pusher or Firebase?**

> **What the interviewer is asking:** "Why did you build the hard part from scratch instead of paying a company to do it?"
> 
> **Your Strong Answer:** "Managed services like Pusher are fantastic for prototyping, but they introduce vendor lock-in and their pricing scales terribly once you hit high concurrent user counts. By engineering the WebSocket Hub myself in Go, I retain complete control over the payload structure, latency, and security. I also needed deep integration with the AI Catch-up feature and the PostgreSQL database, which is much cleaner when you control the entire message pipeline."
> 
> **Translation of technical terms in this answer:**
> - **Vendor lock-in:** When your code is so dependent on a third-party company that you can never switch away.

---

**Q3. Why PostgreSQL with SQLC instead of MongoDB or a Go ORM like GORM?**

> **Your Strong Answer:** "Chat data is highly relational. A Message belongs to a Channel, which belongs to a Workspace, which belongs to a User. Using a NoSQL database like MongoDB would require massive data duplication and manual referential integrity checks. I chose PostgreSQL because it’s ACID compliant. I chose SQLC over an ORM because ORMs add reflection overhead and hide the actual queries being executed. With SQLC, I write highly tuned raw SQL, and it generates type-safe Go code, giving me the performance of a raw driver with the safety of an ORM."
> 
> **Translation of technical terms in this answer:**
> - **Relational:** Data that connects to other data (like branches on a tree).
> - **ACID compliant:** A strict set of database rules that guarantees data is never accidentally deleted or corrupted during a crash.
> - **Reflection overhead:** When the computer wastes time trying to figure out what type of data it is looking at.

---

**Q4. Your AI Catch-up generates JSON instead of just chatting with the user. Why add that complexity?**

> **What the interviewer is asking:** "Why didn't you just let the AI type a paragraph summary like ChatGPT does?"
> 
> **Your Strong Answer:** "Predictability and UX. If I just ask an LLM to 'summarize this', it returns a massive wall of text that looks terrible on a mobile screen. By explicitly forcing the LLM to return a strict JSON schema via `response_format: json_object`, my Go backend can parse that JSON and send it to the frontend. The frontend then renders distinct, beautiful UI components: one card for 'Decisions Made', and another card for 'Action Items' with assignee tags. It turns unstructured AI generation into a structured application feature."
> 
> **Translation of technical terms in this answer:**
> - **Strict JSON schema:** Forcing the AI to format its answer like code, not a letter.

## CATEGORY 2: ARCHITECTURE & EDGE CASES

**Q5. What happens if a user's internet drops while they are connected to the WebSocket Hub?**

> **Your Strong Answer:** "The Hub handles this gracefully. When the underlying TCP connection breaks, the `ReadMessage()` function in the client's read-pump goroutine returns an error. This immediately triggers a `defer` statement that sends the client object to the Hub's `unregister` channel. The Hub removes the user from the active map, closes their write channel, and broadcasts a 'Presence Offline' event to the rest of the channel. No memory leaks, no ghost connections."
> 
> **Translation of technical terms in this answer:**
> - **Read-pump / Defer:** The specific loop listening to the user. "Defer" means "Execute this cleanup code no matter how the loop crashes."

---

**Q6. I run a stress test with 10,000 users all sending messages at the same exact second. Does the server crash?**

> **Your Strong Answer:** "No, because the architecture uses non-blocking channel sends. Inside the Hub's broadcast loop, we use a `select` statement with a `default` case. If a specific client's WebSocket buffer is full because they are on a slow 3G connection and can't receive messages fast enough, the server doesn't freeze waiting for them. The `default` case triggers, immediately closing their connection and kicking them out, ensuring the other 9,999 users experience zero lag."
> 
> **Translation of technical terms in this answer:**
> - **Non-blocking / Buffer:** If you try to hand someone 100 apples and their hands are full (buffer is full), you don't stand there for an hour waiting (blocking). You just drop the apples and walk away (non-blocking). 

---

**Q7. How do you prevent users from reading messages in a private workspace they don't belong to?**

> **Your Strong Answer:** "Two layers of security. First, the REST API endpoints are protected by a JWT Auth middleware that injects the validated User ID into the request context. Second, inside the data access layer, our SQL queries explicitly include a join against the `workspace_members` table. For example, `GetMessages` doesn't just query by `channel_id`, it demands that the `user_id` from the context actually has a row in the membership table. If they don't, the query returns 0 rows, making unauthorized access physically impossible at the database level."
>
> **Translation of technical terms in this answer:**
> - **Request context:** A secure, invisible backpack attached to every web request that carries the user's verified ID so they can't lie about who they are.

---

**Q8. The AI Catch-up feature gets hit hard, and the Groq API rate limits us. What does your pipeline do?**

> **Your Strong Answer:** "First, we mitigate the hit rate using our in-memory `summaryCache` protected by a `sync.Mutex`. If the cached summary is under 5 minutes old, we return it instantly without calling Groq. If we do hit Groq and receive a 429 Rate Limit error, the Go HTTP client reads the non-200 status code and returns a graceful 500 error to the frontend, which displays a toast notification saying 'Summarizer is busy'. The application doesn't crash, the chat continues working, and only the AI feature degrades gracefully."
>
> **Translation of technical terms in this answer:**
> - **sync.Mutex:** A lock. If 5 people try to read the cache at the exact same millisecond, the lock forces them to line up neatly so the computer doesn't crash from reading the exact same piece of memory simultaneously.
> - **Degrades gracefully:** When a car's AC breaks, the car doesn't explode; it just gets hot. If the AI breaks, the chat app keeps working.

---

**Q9. On a 'message_deleted' event, how do you handle it in real-time?**

> **What the interviewer is asking:** "If I delete a message, how does it disappear from everyone else's screen instantly?"
>
> **Your Strong Answer:** "The frontend sends a DELETE request to the REST API. The Go handler executes the `SoftDeleteMessage` SQL query. Upon success, the handler manually constructs a `BroadcastMessage` payload with an event type of `MESSAGE_DELETED` and the `message_id`, and drops it into the WebSocket Hub's broadcast channel. The frontend clients receive this event, find the message ID in their local DOM, and instantly apply a CSS fade-out animation to remove it."
>
> **Let's explain this in extremely simple English:**
> You delete a message. The database updates. Then the server screams down the tunnel to everyone: "HEY! Erase Message #55 from your screen right now!"

**Q10. The WebPush Worker crashes halfway through sending 100 notifications. What state is your system in?**

> **Your Strong Answer:** "The main chat server is pristine because the workers run on isolated goroutines. If a worker panics, only that goroutine dies. To make it bulletproof, I would wrap the worker loop in a `defer recover()` block to catch panics and respawn the worker. However, the tasks in the current memory queue might be lost on a full server crash. If this were enterprise-scale, I would move the `TaskQueue` from an in-memory Go channel to a durable Redis queue or RabbitMQ."
>
> **Translation of technical terms in this answer:**
> - **defer recover():** A magic spell in Go that says, "If this code crashes and is about to kill the server, catch the crash, print an error, and keep the server alive."
> - **Durable Redis queue:** Saving the task list to a hard drive instead of RAM, so if the server loses power, it remembers what tasks it didn't finish.

**Q13. We now have 3 years of historical messages and Postgres is starting to struggle. How do you fix it?**

When a user opens a chat, they usually only request the last 50 messages, which all live in the most recent partition. PostgreSQL's query planner automatically prunes the older 35 months of data and only scans the current month. This keeps index sizes small and read times lightning fast even as data grows exponentially."

> **Translation of technical terms in this answer:**

## CATEGORY 4: PROVE YOU BUILT IT (The Hardest Bugs)

**Q15. What was the most confusing bug you hit while building the WebSocket Hub?**

> **Your Strong Answer:** "Concurrent map writes. Early on, my server crashed randomly with a fatal error: 'concurrent map read and map write'. I had multiple client goroutines trying to register themselves into the Hub's `clients` map at the exact same millisecond. I realized Go maps are not thread-safe. I fixed it by moving all map modifications (adding/removing clients) into the Hub's central `Run()` loop, which processes requests sequentially via the `register` and `unregister` channels. This completely eliminated the race condition without needing slow Mutex locks."
>
> **Translation of technical terms in this answer:**
> - **Concurrent map write / Race condition:** Imagine two people trying to write their name on the exact same line of a sign-up sheet at the exact same time with two different pens. The paper rips. That's what happens to the server. The fix was forcing them to stand in a single-file line (channels).

**Q16. You're using JWTs for authentication. What's the trap when using WebSockets?**

> **Your Strong Answer:** "You can't send standard HTTP Authorization headers when initiating a WebSocket connection from the browser's native API. I spent hours wondering why my middleware was rejecting the WebSocket upgrade. The fix was passing the JWT token as a URL query parameter (`?token=xyz`) during the handshake. In the Go handler, I extracted the token from the URL, validated the JWT signature, and only then upgraded the HTTP connection to a WebSocket connection."
> 
> **Translation of technical terms in this answer:**
> - **WebSocket upgrade:** A WebSocket connection starts its life as a normal HTTP web request, and then says, "Hey server, can we upgrade this to a permanent connection?"

**Q17. The frontend UI was flickering every time a new message arrived. How did you solve it?**

> **Your Strong Answer:** "I had an issue where incoming WebSocket messages were re-rendering the entire chat container, causing the scroll position to jump violently. I implemented DOM diffing and appending. Instead of wiping the `innerHTML`, I used `insertAdjacentHTML('beforeend', template)` to append only the new message node. Furthermore, I built a smart scroll lock: if the user had scrolled up to read history, the UI would not snap them to the bottom when a new message arrived, preserving their reading context."

> **Translation of technical terms in this answer:**
> - **DOM diffing / append:** Instead of erasing the whole screen and redrawing 100 messages, just glue the 1 new message to the very bottom.

## CATEGORY 5: SYSTEM DESIGN INTERVIEW (Architecting a Real-Time Chat App with AI)

*System Design interviews test your ability to zoom out. You need to explain how all the pieces fit together, how data flows, and how the system scales when you go from 1,000 users to 1 Million users.*

### Step 1: The Core Requirements (What are we building?)
**Functional Requirements (What it must do):**
- Users can send and receive messages in real-time.
- Messages are stored permanently so offline users can read them later.
- AI can summarize missed messages into action items.
- Offline users get push notifications.

**Non-Functional Requirements (How well it must do it):**
- **Low Latency:** Real-time messages must appear instantly (<100ms).
- **High Availability:** The chat shouldn't go down.
- **Scalability:** It should handle a massive spike in concurrent users.

### Step 2: The High-Level Architecture (The Bird's Eye View)
Imagine you draw this on a whiteboard. Here is the flow:
1. **Client (Vanilla JS):** Connects to the backend via an open WebSocket tunnel.
2. **API/WebSocket Server (Go):** The brain. It has the `Hub` to route real-time messages and `Handlers` for REST API calls (like the AI Catch-up).
3. **Database (PostgreSQL):** The source of truth for messages, channels, and users.
4. **Cache (In-Memory/Redis):** Temporarily stores AI summaries and active session data to prevent spamming the database or AI APIs.
5. **Worker Pool (Go Goroutines):** A background team that handles slow tasks (like pushing notifications) so the main chat server stays blazing fast.
6. **External APIs (Groq/Llama 3):** The third-party AI brain we call to summarize transcripts.

### Step 3: Database Schema Design
*Keep it simple but highly relational.*
- **Users:** `id, username, email, password_hash`
- **Workspaces:** `id, name, created_by`
- **Channels:** `id, workspace_id, name`
- **Messages:** `id, channel_id, user_id, content, created_at`
*(Crucial Index: `CREATE INDEX ON messages (channel_id, created_at DESC)` because we almost always query messages by channel, sorted by time.)*

### Step 4: Scaling the Real-Time Layer
Right now, our Go `Hub` holds all WebSocket connections in memory. If the server crashes, everyone disconnects. 
**How to scale it:** We add multiple Go servers. But if John is connected to Server A, and Sarah is on Server B, how does John's message reach Sarah?
**The Solution (Pub/Sub):** We introduce **Redis Pub/Sub**. When John sends a message to Server A, Server A publishes it to a Redis channel. Server B is subscribed to that Redis channel, hears the message, and pushes it down Sarah's WebSocket.

### Step 5: System Design Interview Questions & Follow-Ups

**Q1. Let's talk about the AI Catch-up. The Groq API is taking 3 seconds to respond. 10 users click the button repeatedly at the same time. How do you architect this to be resilient?**
> **Your Answer:** "Right now, I have an in-memory `summaryCache` protected by a Mutex lock. If I were scaling this to millions of users, I would move the cache to **Redis** with a 5-minute TTL (Time To Live). When a user clicks 'Catch-up', the backend checks Redis. If the summary is there, it returns it instantly. If not, the backend puts a 'processing' lock in Redis and makes the Groq API call. The frontend shows a loading spinner. If the other 9 users click the button during those 3 seconds, the backend sees the 'processing' lock and just tells them to wait for the single API call to finish. This saves us massive API costs and prevents rate-limiting."
> **Follow-up:** *What if the chat channel has 10,000 missed messages? The LLM has a token limit and will crash if you send them all at once.*
> **Answer:** "We have to implement **Chunking and Map-Reduce**. We break the 10,000 messages into chunks of 1,000. We ask the LLM to summarize each chunk in parallel (Map). Then, we take the 10 smaller summaries and ask the LLM to summarize those into one final master summary (Reduce). We would absolutely move this heavy processing to our background Worker Pool so it doesn't block the HTTP server."

**Q2. How do you handle message ordering and guarantee a message isn't sent twice if the internet flickers? (Idempotency)**
> **Your Answer:** "If a user has a bad connection, their browser might retry sending the same message. To fix this, the frontend generates a unique `UUID` (Universally Unique Identifier) for the message *before* sending it over the WebSocket. The backend checks the database: if a message with that UUID already exists, it simply ignores the duplicate. For true message ordering, we strictly rely on the database's `created_at` timestamp, not the client's local time, because client clocks can easily be wrong."
> **Follow-up:** *What if two messages arrive at the exact same millisecond?*
> **Answer:** "We use a sequence number or a high-precision monotonic clock in Postgres to break ties. Alternatively, if they truly land at the exact same millisecond, the UI rendering order doesn't technically matter as long as all clients agree on the order provided by the database."

**Q3. Our app goes viral. We hit 1 Million concurrent users. The Postgres database is catching fire. How do you scale the database?**
> **Your Answer:** "First, I add **Read Replicas**. 90% of chat app traffic is reading old messages, not writing new ones. We route all `SELECT` queries to replica databases, taking the read load entirely off the primary master database. Second, I implement **Caching** (Redis) for frequently accessed data like user profiles. If that's not enough, I would **Partition** the messages table by date (e.g., one table partition per month) so queries for recent messages are blazing fast because the database ignores years of old data."
> **Follow-up:** *What if the writes are too heavy? A read replica only helps with reads.*
> **Answer:** "Then we must **Shard** the database. We can shard by `workspace_id`. This means Workspace A's data lives on Database Server 1, and Workspace B's data lives on Database Server 2. Since users in Workspace A rarely interact with Workspace B, this splits the write load perfectly without breaking our relational model."

**Q4. How does the system know when a user is "Offline" to send them a Push Notification?**
> **Your Answer:** "Our Go WebSocket `Hub` maintains a map of active connections. When a message is broadcast to a channel, the server cross-references the channel's member list against the active connections map. If Sarah is a member but not in the active map, the server immediately drops a 'Send WebPush to Sarah' task into the asynchronous Go Worker Pool."
> **Follow-up:** *What if Sarah is online, but on her phone, and she closed the app to look at Instagram? Her WebSocket disconnected.*
> **Answer:** "Exactly, that's why WebPush and Service Workers are critical. Since she disconnected her WebSocket, our Hub flags her as offline. The Worker Pool sends the push notification payload to Apple/Google's servers. Even though our web app is fully closed, her phone's OS receives the push, wakes up our background `sw.js` (Service Worker), and displays the native banner notification on her screen."

**Q5. You used a single Go server. What happens if the server crashes in the middle of processing 50 push notifications in the Worker Pool?**
> **Your Answer:** "Right now, they use an in-memory Go channel as a queue, meaning those 50 tasks would unfortunately be lost in RAM upon a full server crash. To make it enterprise-grade, I would decouple the task queue using a durable message broker like **RabbitMQ**, **Kafka**, or **Redis Streams**. When the server realizes Sarah needs a notification, it publishes a task payload to RabbitMQ. The workers consume from RabbitMQ. If a worker crashes halfway through sending the push, it never sends the 'acknowledgement' to RabbitMQ, so RabbitMQ safely gives the task to another worker. Zero lost notifications."

## GO & WEB CONCEPTS — EXPLAIN COLD

| Concept | Explanation |
|---------|-------------|
| Goroutine | A lightweight, virtual thread managed by the Go runtime. Costs 2KB of memory. You can run 100,000 of them easily. |
| Go Channel | A thread-safe pipe that allows two goroutines to send data to each other safely without causing race conditions. |
| `select` statement | A Go feature that lets a goroutine wait on multiple channels at once. Essential for non-blocking operations. |
| SQLC | A compiler that takes raw SQL queries and automatically writes perfect, type-safe Go code to execute them. |
| Mutex (`sync.Mutex`) | A digital padlock. If two pieces of code try to edit the same memory at the exact same time, it locks one out until the other finishes. |
| JWT (JSON Web Token) | A secure, cryptographically signed VIP pass given to the user after login. Proves who they are without needing database lookups. |
| WebSockets | A permanent, open phone line between the browser and the server, allowing the server to push data instantly. |
